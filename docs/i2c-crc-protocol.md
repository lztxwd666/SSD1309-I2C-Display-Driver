# I2C 帧 Modbus CRC16 接收端规范

协议版本：v2（带长度字段与末字节 NACK）

给接收端开发者的精简适配版：[i2c-crc-quickstart.md](i2c-crc-quickstart.md)。本文档保留完整细节、边界条件与参考实现。

本文档规定 SSD1309 I2C 显示驱动与通讯对端之间的线协议：所有 I2C 数据帧末尾附加 Modbus CRC16，写帧带 1 字节载荷长度；接收端在最后一个字节的 ACK 周期校验失败时 NACK，发送端据此立即感知。适用于 MCU 桥接器、协议模拟器或任何接收 SSD1309 命令/数据流的设备。

驱动侧（Rust `i2c_display_driver` 与纯 Python `ssd1309_driver`）已按本规范实现。对端必须按本规范解析、校验并回传，否则 CRC 字节会被当作 SSD1309 命令或 GDDRAM 数据执行。

> 重要限制：原生 SSD1309 面板不支持 CRC。对端必须缓存完整帧、校验 CRC、剥离长度字节与末尾 2 字节 CRC 后，再把剩余的命令/数据转发给面板。不可把长度字节或 CRC 字节转发给面板。

## 1. 帧单位

- **帧**：一次 I2C 写事务（START → 从机地址+W → 字节流 → STOP）为一条写帧；一次 I2C 读事务（START → 从机地址+R → 字节流 → STOP）为一条读响应帧。
- 每条帧独立计算 CRC，不跨事务累计，也不把多个事务拼成一条帧。
- CRC **不覆盖** I2C 从机地址与 R/W 位（由 I2C 控制器插入，驱动无法参与），只覆盖控制字节、长度字节及其后的载荷。
- 主机对状态寄存器的读取是“先写 4 字节请求帧、STOP、再单独发起读事务”的两段式流程，不使用 repeated start。

## 2. 术语

| 术语            | 含义                                                             |
| --------------- | ---------------------------------------------------------------- |
| 控制字节        | 帧体第一个字节：`0x00` 表示命令流，`0x40` 表示 GDDRAM 数据流     |
| 长度字节        | 帧体第二个字节：载荷字节数（0..=255）                            |
| 帧体（body）    | 去掉末尾 2 字节 CRC 后的完整字节序列：控制字节 + 长度字节 + 载荷 |
| 载荷（payload） | 长度字节之后的命令或 GDDRAM 数据                                 |
| 命令帧          | 控制字节 `0x00`、长度 ≥ 1 的写帧                                 |
| 数据帧          | 控制字节 `0x40` 的写帧                                           |
| 状态读请求      | 控制字节 `0x00`、长度 `0x00` 的写帧，线上完整帧为 `00 00 01 B0`  |
| 状态读响应      | 主机读事务返回的 3 字节：状态字节 + CRC                          |
| 末字节 NACK     | 接收端在 CRC_H 的 ACK 周期返回 NACK，表示帧被拒绝                |
| pending 读      | 接收端收到合法状态读请求后置位的待读标志                         |

## 3. 帧格式

### 3.1 帧类型总表

| 帧类型     | 方向          | 线上字节                                         | CRC 覆盖                     |
| ---------- | ------------- | ------------------------------------------------ | ---------------------------- |
| 命令帧     | 主机 → 接收端 | `0x00` + `len` + 命令载荷 + `CRC_L` + `CRC_H`    | `0x00` + `len` + 命令载荷    |
| 数据帧     | 主机 → 接收端 | `0x40` + `len` + GDDRAM 数据 + `CRC_L` + `CRC_H` | `0x40` + `len` + GDDRAM 数据 |
| 状态读请求 | 主机 → 接收端 | `0x00` + `0x00` + `CRC_L` + `CRC_H`              | `0x00` + `0x00`              |
| 状态读响应 | 接收端 → 主机 | 状态字节 + `CRC_L` + `CRC_H`（3 字节）           | 状态字节                     |

- 写帧总长度 = `len + 4`（控制 1 + 长度 1 + 载荷 len + CRC 2）。
- 状态读请求的 `len = 0`，总长度 4 字节。
- 状态读响应保持 3 字节，不带长度字段；主机固定读取 3 字节。
- CRC 两字节按 **低字节在前** 追加（与 Modbus RTU 一致）：`CRC_L = crc & 0xFF`，`CRC_H = crc >> 8`。

### 3.2 长度

| 项目                              | 数值                                                |
| --------------------------------- | --------------------------------------------------- |
| 驱动单帧载荷上限（Rust / Python） | 255 字节                                            |
| 驱动单帧最大线上长度              | 259 字节（1 控制 + 1 长度 + 255 载荷 + 2 CRC）      |
| 实际常用数据帧长度                | 132 字节（1 + 1 + 128 + 2）                         |
| 实际命令帧长度                    | 5 到 11 字节（例如单命令 5 字节，硬件滚动 11 字节） |
| 状态读请求长度                    | 4 字节                                              |
| 状态读响应长度                    | 3 字节                                              |
| 接收端最低要求                    | 至少支持 259 字节写帧缓存                           |

接收端必须按“先收完整帧、再执行”的顺序工作；不允许边接收边转发，否则 CRC 校验失败时无法保证整帧不执行。

### 3.3 帧示例

| 用途                         | 线上完整帧          |
| ---------------------------- | ------------------- |
| 命令 0xAE（关闭显示）        | `00 01 AE F1 EC`    |
| 命令 0x81 0xCF（设置对比度） | `00 02 81 CF 81 E0` |
| 命令 0x20 0x02（页寻址模式） | `00 02 20 02 39 E5` |
| 命令 0xB0（页地址 0）        | `00 01 B0 71 E4`    |
| 命令 0x00 0x10（列地址 0）   | `00 02 00 10 A0 28` |
| 数据 0x01 0x02               | `40 02 01 02 34 75` |
| 状态读请求                   | `00 00 01 B0`       |
| 状态 0x00 的读响应           | `00 BF 40`          |
| 状态 0x01 的读响应           | `01 7E 80`          |
| 状态 0x81 的读响应           | `81 7F 20`          |

状态读请求是 4 字节写事务（`00 00 01 B0`），状态读响应是 3 字节读事务（如 `01 7E 80`），由 I2C 的 R/W 位区分。

## 4. CRC16 规范

### 4.1 参数

| 参数               | 值                            |
| ------------------ | ----------------------------- |
| 算法名称           | CRC-16/MODBUS                 |
| 宽度               | 16                            |
| 多项式             | 0x8005（反射实现使用 0xA001） |
| 初值               | 0xFFFF                        |
| 输入反射（refin）  | 是                            |
| 输出反射（refout） | 是                            |
| 最终异或（xorout） | 0x0000                        |
| 标准检查值         | `"123456789"` → 0x4B37        |
| 追加字节序         | 低字节在前                    |

### 4.2 计算对象

CRC 覆盖“去掉末尾 2 字节 CRC 后的整条帧体”：

- 命令帧：`0x00` + `len` + 命令载荷
- 数据帧：`0x40` + `len` + GDDRAM 数据
- 状态读请求：`0x00` + `0x00`
- 状态读响应：状态字节

不要把 I2C 地址、R/W 位、CRC 自身计入 CRC。Modbus CRC 有一个可直接用于自检的性质：对“帧体 + CRC”整帧重新计算，结果应为 0。

## 5. 接收端处理流程

### 5.1 写事务与末字节 NACK

接收端必须在接收过程中维护字节计数，并在 CRC_H 的 ACK 周期做出 ACK/NACK 决定：

```text
收到写事务字节流：

1. 接收控制字节 frame[0]
2. 接收长度字节 frame[1]，payload_len = len
3. expected_total = payload_len + 4
   若 expected_total > 接收缓冲上限：在长度字节的 ACK 周期 NACK，丢弃
4. 继续接收；每收到一个字节递增计数
5. 当收到第 expected_total 个字节（索引 payload_len + 3，即 CRC_H）时：
   5.1 若控制字节不是 0x00/0x40：NACK 本字节，丢弃
   5.2 计算 crc = modbus_crc16(frame[0 .. payload_len + 2])
   5.3 读取 CRC_L = frame[payload_len + 2]，CRC_H = frame[payload_len + 3]
   5.4 若 crc != CRC_L | (CRC_H << 8)：NACK 本字节，丢弃
   5.5 否则 ACK 本字节，等待 STOP
6. 若在 expected_total 之前收到 STOP：长度不足，丢弃；STOP 之后无法 NACK，
   记录长度错误（见 11 节已知限制）
7. 若在 expected_total 之后仍有字节：在第一个多余字节的 ACK 周期 NACK，
   丢弃整帧（尚未执行）
8. 若收到正常 STOP 且 CRC_H 已 ACK：执行 frame[0 .. payload_len + 2]
```

关键要求：

- **NACK 必须发生在最后一个字节（CRC_H）的 ACK 周期**；此时接收端已收到完整帧，可以计算 CRC。发送端看到的是整帧写事务失败。
- 接收端必须先缓存完整帧，校验通过且收到 STOP 后才执行；CRC 失败或 STOP 前长度不符时不得执行任何部分。
- 长度字节与载荷都在 CRC 保护范围内，接收端应使用 `payload_len` 计算帧尾，不能用固定长度假设。
- 若 `payload_len` 超过接收缓冲上限，应在长度字节处立即 NACK；这能避免为明显非法帧分配/等待。
- 接收端应在 100 kHz 下可靠完成上述判断。CRC 可随字节增量计算，最后一个字节的 ACK 周期只需完成最后一次迭代与比较。
- ACK CRC_H 表示帧已被接收并即将执行；NACK CRC_H 表示帧被丢弃，主机会重试。

### 5.2 状态读取时序

状态读取固定为以下时序：

```text
主机                                 接收端
 |---- 写事务: 00 00 01 B0 ---------->|
 |                                    | 校验长度与 CRC
 |                                    | ACK CRC_H
 |                                    | pending = true
 |                                    | 采样/缓存状态字节
 |<---- STOP -------------------------|
 |                                    |
 |---- 读事务: 读取 3 字节 ---------->|
 |<--- 状态字节, CRC_L, CRC_H --------|
 |                                    | pending = false
```

要求：

- 状态读请求帧必须是 `00 00 01 B0`（控制 0x00、长度 0x00）。接收端不能把它当成空命令帧执行。
- 主机随后会读取 **恰好 3 字节**；不足 3 字节时主机会报状态帧长度错误。
- 状态读响应的 CRC 只覆盖状态字节，不含请求帧。
- 建议在收到读请求时就采样并缓存状态，主机读事务到来时直接返回缓存值，避免依赖 clock stretching 或下游总线延迟。
- 若对端是透明桥接且无法在写事务阶段采样面板状态，可在读事务阶段读取面板，但必须确保能在主机 I2C 超时内完成。
- pending 读标志只由后续读事务消费；任何写事务都应先清除它，合法读请求在校验通过后重新置位。
- 未收到合法读请求时发生的读事务不属于本协议。接收端不得返回未加 CRC 的裸字节；建议不返回数据（主机将得到短读错误），或返回一条 CRC 合法的默认状态帧。具体默认值由对端自行约定，但必须保持 CRC 合法。

状态字节沿用 SSD1309 状态寄存器定义：bit7 = 忙，bit0 = 电荷泵（DC-DC 升压器）使能。透明桥接应返回面板真实状态；模拟器可返回 0x01（不忙、电荷泵已使能）。

### 5.3 透明桥接映射

若接收端是“主机 I2C 从机 + 面板 I2C 主机”的透明桥接器：

| 收到的主机帧             | 校验通过后的动作                                                           |
| ------------------------ | -------------------------------------------------------------------------- |
| 命令帧 `00 len ... CRC`  | 去掉长度字节与末尾 2 字节 CRC，把 `00 ...` 原样转发给面板                  |
| 数据帧 `40 len ... CRC`  | 去掉长度字节与末尾 2 字节 CRC，把 `40 ...` 原样转发给面板                  |
| 状态读请求 `00 00 01 B0` | 向面板发起原 `00` 状态读取，得到 1 字节状态；向主机返回 `状态 CRC_L CRC_H` |

除每帧多 1 字节长度与 2 字节 CRC 外，主机与面板之间的命令/数据内容、初始化序列、页寻址方式均与原有驱动完全一致。

## 6. 发送端行为（驱动侧）

驱动侧（Rust `I2cBus` / Python `I2cBus`）按以下规则工作：

1. 按第 3 节组装写帧：控制 + 长度 + 载荷 + CRC。
2. 调用 `write()` 发送整帧；接收端在 CRC_H 的 ACK 周期返回 NACK 时，Linux i2c-dev 通常返回 `-EREMOTEIO`（errno 121），也有控制器/内核可能映射为其他错误，需在目标平台实测确认。
3. 发送端只对 `EREMOTEIO` 重试（当前策略视为接收端拒绝本帧），最多重试 2 次（共 3 次发送）；每次重试都是完整一帧，接收端按新帧处理。
4. 3 次均被 NACK 后，返回“帧校验失败”错误：
   - Rust：`I2cBus` 返回 `io::ErrorKind::InvalidData`；`Display` 层映射为 `DriverError::FrameRejected`
   - Python：`I2cBus` 抛出 `FrameRejectedError`；`Display` 层原样传播
5. `render_robust()` 对这种错误只跳过本显示帧、计入 `frames_rejected` / `frames_skipped`，**不重置 I2C 总线**；总线错误（`EIO`、`ENXIO` 等）仍走原有 `recover()` 路径。
6. `EREMOTEIO` 的语义因控制器/内核而异：RP1/DesignWare 对地址 NACK、SDA stuck 也可能返回该 errno。当前发送端策略把 `EREMOTEIO` 一律视为帧拒绝并重试，不触发总线恢复；这是既定取舍。`ENXIO` 通常表示从机/适配器不存在，`EIO` 通常为总线错误，这两类不按帧拒绝重试。

重试是安全的：接收端在 CRC 失败时整帧丢弃、不执行；同一帧被重发时按新帧重新校验。命令/数据写入对同一目标重复执行通常是幂等的（设置寄存器、写同一 GDDRAM 地址），因此重试不会改变最终显示结果。

## 7. 错误处理矩阵

| 条件                          | 接收端必须行为                                       | 建议行为                                 |
| ----------------------------- | ---------------------------------------------------- | ---------------------------------------- |
| 写帧 CRC 不匹配               | **NACK `CRC_H`**，整帧丢弃，不执行任何部分           | 记录 CRC 错误计数                        |
| 控制字节不是 0x00/0x40        | NACK `CRC_H`（或不早于长度字节的某个字节），丢弃     | 记录协议错误计数                         |
| `len` 导致总长度超过接收缓冲  | 在长度字节的 ACK 周期 NACK，丢弃                     | 记录长度错误计数                         |
| 帧在 `CRC_H` 之前收到 STOP    | 丢弃；无法在 STOP 后 NACK                            | 记录长度错误；等待主机下一帧             |
| 收到超过 `len + 4` 的多余字节 | 在第一个多余字节的 ACK 周期 NACK，丢弃整帧（未执行） | 记录长度错误                             |
| 状态读请求 CRC 不匹配         | NACK `CRC_H`，不置 pending                           | 记录 CRC 错误                            |
| 主机读时无 pending 读         | 不返回未加 CRC 的数据                                | 返回 0 字节/NAK，或 CRC 合法的默认状态帧 |
| 主机读取字节数不足 3          | 主机侧会报错                                         | 接收端应保证返回恰好 3 字节              |
| 命令/数据载荷内容非法         | 按现有 SSD1309 行为处理                              | 与本协议无关，不额外要求                 |

硬性要求：**CRC 或长度校验失败的帧不得执行任何一部分，且必须 NACK `CRC_H`（长度超缓冲时 NACK `len`）。** NACK 是 v2 的强制反馈，不是可选项；接收端不得用 ACK 表示接受后再静默丢弃，否则发送端无法感知丢帧，重试与帧拒绝语义失效。

## 8. 对端验收清单

必须满足：

- [ ] CRC16 算法与本规范 4.1 一致，标准检查值 `"123456789"` 为 0x4B37
- [ ] CRC 按低字节在前追加与解析
- [ ] 写帧解析 `len`，按 `len + 4` 计算帧尾
- [ ] 在 `CRC_H` 的 ACK 周期校验 CRC；失败时 NACK 该字节
- [ ] CRC 失败时整帧丢弃，不执行任何一部分；成功时 ACK，收到 STOP 后执行
- [ ] 能识别 `00 00 01 B0` 为状态读请求，而不是空命令帧
- [ ] 状态读响应返回恰好 3 字节，CRC 仅覆盖状态字节
- [ ] 任何新写事务都会清除 pending 读标志
- [ ] 不把长度字节、CRC 字节转发给 SSD1309
- [ ] 至少支持 259 字节写帧缓存
- [ ] 重试帧按全新帧处理，不把前一次的 NACK 状态带入

建议满足：

- [ ] CRC 错误、长度错误、非法控制字节分别计数
- [ ] 收到读请求时立即采样并缓存状态，避免读事务阶段等待
- [ ] pending 读设置超时（例如 1 秒），防止异常时序下长期滞留
- [ ] 在逻辑分析仪上确认 NACK 出现在 `CRC_H` 的 ACK 周期

## 9. 一致性测试向量

接收端应能对以下帧给出完全一致的判定：

| 完整帧                     | 期望动作                                                                         |
| -------------------------- | -------------------------------------------------------------------------------- |
| `00 01 AE F1 EC`           | 校验通过，ACK，执行命令 `AE`                                                     |
| `00 01 AE F1 ED`           | CRC 失败，NACK `CRC_H`，丢弃，不执行                                             |
| `00 02 81 CF 81 E0`        | 校验通过，ACK，执行命令 `81 CF`                                                  |
| `00 02 20 02 39 E5`        | 校验通过，ACK，执行命令 `20 02`                                                  |
| `00 01 B0 71 E4`           | 校验通过，ACK，执行命令 `B0`                                                     |
| `00 02 00 10 A0 28`        | 校验通过，ACK，执行命令 `00 10`                                                  |
| `40 02 01 02 34 75`        | 校验通过，ACK，写入数据 `01 02`                                                  |
| `40 02 01 02 34 76`        | CRC 失败，NACK `CRC_H`，丢弃                                                     |
| `00 00 01 B0`              | 校验通过，ACK，置 pending 读，不执行命令                                         |
| `00 00 01 B1`              | CRC 失败，NACK，不置 pending                                                     |
| `41 00 31 E0`              | CRC 通过但控制字节非法，NACK `CRC_H`，丢弃                                       |
| `00 03 AE F0 8C`           | 长度字段要求 7 字节，实际只收到 5 字节；STOP 早于帧尾，丢弃（无法 NACK）         |
| `00 01 AE F1 EC 00`        | 期望 5 字节，收到 6 字节；第 6 字节为多余字节，NACK 该字节，丢弃整帧（尚未执行） |
| 主机读且 pending=状态 0x01 | 返回 `01 7E 80`                                                                  |
| 主机读且 pending=状态 0x81 | 返回 `81 7F 20`                                                                  |

CRC 算法自检：对帧体 `01 03 00 00 00 0A` 计算 CRC 应为 0xCDC5，追加后线上字节为 `01 03 00 00 00 0A C5 CD`。

## 10. 联调步骤

1. **静态向量**：用附录 A 或附录 B 的参考实现跑第 9 节全部向量，确认 CRC 与帧判定一致。
2. **NACK 时序**：用逻辑分析仪抓 `00 01 AE F1 EC` 与破坏 CRC 后的 `00 01 AE F1 ED`，确认接收端在最后一个字节的 ACK 周期返回 NACK。
3. **线上字节**：确认初始化命令帧、132 字节数据帧、状态读请求 `00 00 01 B0` 与 3 字节响应。
4. **接面板**：在接收端完成 CRC 校验与剥离后，运行驱动示例 `smoke`、`selftest`、`diag`，确认显示内容与状态读取正常。
5. **故障注入**：运行时人为破坏某一帧的 CRC 字节，确认接收端 NACK、发送端重试、屏幕内容不变；破坏读响应 CRC，确认驱动 `read_status()` 返回帧校验失败。
6. **长稳**：运行 `stress` 示例，确认长时间运行下无 CRC 误判、无状态错位。

## 11. 兼容性与已知限制

- 协议版本 v2 固定为：写帧控制 + 长度 + 载荷 + CRC、低字节在前、接收端在 `CRC_H` NACK、状态读请求带长度、状态读响应 3 字节。
- v2 与 v1 不兼容；原生 SSD1309 面板不能直连本协议；未升级的接收端也不能与本驱动通信。
- I2C 总线速率仍为 100 kHz，本协议不改变时序要求。
- 自定义 `I2cDevice`/`Display::from_device` 传输实现不经过 `I2cBus`，如需 CRC 必须自行实现本规范。
- **已知限制**：若长度字节本身被干扰成比实际载荷更大的值，接收端会等待帧尾直到 STOP，而 STOP 之后无法再 NACK，发送端可能认为写入成功；接收端应丢弃并记录长度错误。若需要覆盖这种极低概率情况，可在应用层增加周期性链路状态查询（错误计数/最后错误帧），本规范暂不定义该可选查询帧。发送端的 `frames_rejected` 只统计 NACK 拒绝的推帧；这种静默丢帧不会计入，命令帧需要应用层周期性重发。
- 发送端对 NACK 的重试最多 2 次；重试期间接收端可能已部分接收前一帧（但 CRC 失败帧不会执行），因此对端必须保证“校验失败即完全不执行”。
- Linux `EREMOTEIO` 到帧拒绝的映射需在目标内核与 I2C 控制器（树莓派 RP1）上实测确认；RP1/DesignWare 的地址 NACK、SDA stuck 也可能返回 `EREMOTEIO`，当前发送端统一按帧拒绝处理。若实际返回其他错误码，需在驱动 `is_data_nack` 中等价映射。

## 附录 A：C99 参考实现

```c
#include <stddef.h>
#include <stdint.h>

/* 计算 Modbus CRC16。标准检查值："123456789" -> 0x4B37。 */
uint16_t modbus_crc16(const uint8_t *data, size_t len)
{
    uint16_t crc = 0xFFFFu;
    for (size_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i];
        for (int bit = 0; bit < 8; bit++) {
            if (crc & 0x0001u) {
                crc = (uint16_t)((crc >> 1) ^ 0xA001u);
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;
}

/* 组装 v2 写帧：控制 + 长度 + 载荷 + CRC。返回帧总长度。 */
size_t frame_build_v2(uint8_t control, const uint8_t *payload, size_t payload_len,
                      uint8_t *out)
{
    out[0] = control;
    out[1] = (uint8_t)payload_len;
    for (size_t i = 0; i < payload_len; i++) {
        out[2 + i] = payload[i];
    }
    uint16_t crc = modbus_crc16(out, 2 + payload_len);
    out[2 + payload_len] = (uint8_t)(crc & 0xFFu);
    out[3 + payload_len] = (uint8_t)(crc >> 8);
    return payload_len + 4;
}

/*
 * 校验完整 v2 写帧。
 * 返回 0 成功，并通过 payload_len 输出载荷长度；
 * 返回 -1 长度或控制字节非法；返回 -2 CRC 错误。
 */
int frame_verify_v2(const uint8_t *frame, size_t len, size_t *payload_len)
{
    if (len < 4) {
        return -1;
    }
    if (frame[0] != 0x00 && frame[0] != 0x40) {
        return -1;
    }
    size_t plen = frame[1];
    if (len != plen + 4) {
        return -1;
    }
    uint16_t expected = modbus_crc16(frame, plen + 2);
    uint16_t received = (uint16_t)frame[plen + 2] | ((uint16_t)frame[plen + 3] << 8);
    if (received != expected) {
        return -2;
    }
    *payload_len = plen;
    return 0;
}
```

## 附录 B：Python 参考实现

```python
def modbus_crc16(data: bytes) -> int:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte
        for _ in range(8):
            if crc & 0x0001:
                crc = (crc >> 1) ^ 0xA001
            else:
                crc >>= 1
    return crc & 0xFFFF


def append_crc(data: bytes) -> bytes:
    crc = modbus_crc16(data)
    return data + bytes((crc & 0xFF, crc >> 8))


def build_frame_v2(control: int, payload: bytes) -> bytes:
    if len(payload) > 255:
        raise ValueError("载荷超过 255 字节")
    return append_crc(bytes((control, len(payload))) + payload)


def parse_frame_v2(frame: bytes) -> bytes:
    if len(frame) < 4:
        raise ValueError(f"帧长度不足: {len(frame)} < 4")
    control = frame[0]
    if control not in (0x00, 0x40):
        raise ValueError(f"控制字节非法: 0x{control:02X}")
    payload_len = frame[1]
    if len(frame) != payload_len + 4:
        raise ValueError(
            f"帧长度不符: 期望 {payload_len + 4} 字节，实际 {len(frame)} 字节"
        )
    body = frame[:-2]
    expected = modbus_crc16(body)
    received = frame[-2] | (frame[-1] << 8)
    if received != expected:
        raise ValueError(
            f"CRC 校验失败: 接收 0x{received:04X}，计算 0x{expected:04X}"
        )
    return frame[2:-2]
```
