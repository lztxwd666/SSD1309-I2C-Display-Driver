# I2C 帧 Modbus CRC16 协议 v3

当前 Rust / Python 驱动实现本协议的主机端。接收端开发者可先看 [v3 接收端速查](i2c-crc-quickstart.md)。历史格式见 [v2 规范](i2c-crc-protocol-v2.md)和 [v2 接收端速查](i2c-crc-quickstart-v2.md)。

v3 在标准 I2C 事务上增加带序号的写帧与可重复读取的链路回执。接收端在 STOP 后判定整帧结果。主机确认当前帧成功后才发下一帧。v3 与 v2 的线上格式、读语义均不兼容。驱动须配套使用 v3 接收端。

## 1. 事务边界与 CRC

- 写帧为一次独立的 `START → 地址+W → 帧字节 → STOP`。接收端在正常接收过程中按 I2C 规则 ACK。长度、控制字节和 CRC 的判定结果由链路回执报告。地址 NACK、硬件错误及控制器超时仍按 I2C 传输错误处理。
- 主机以独立的 `START → 地址+R → 6 字节 → STOP` 读取回执，无需发送选择请求。协议要求写事务以 STOP 结束。若写事务遇到 repeated START，接收端丢弃该写帧，禁止因 repeated START 而提交写入。
- CRC-16/MODBUS 使用多项式 `0x8005`（反射实现 `0xA001`）、初值 `0xFFFF`、输入和输出反射、最终异或 `0x0000`。检查值 `"123456789" → 0x4B37`。CRC 按低字节在前传输，覆盖帧中 CRC 之前的所有字节。I2C 从机地址、R/W 位、应答位和总线时序均在覆盖范围之外。

标准 I2C 读事务的最后一个字节由主机发 NACK 结束。接收端完成发送时保留回执，以便主机在发现 CRC 错误或短读后再次读取。 [NXP UM10204 §3.1.6、§3.1.10](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)

## 2. 写帧格式

```text
type | len | seq_L | seq_H | payload[len] | CRC_L | CRC_H
```

`len` 为载荷字节数，`seq_L | seq_H` 为低字节在前的 16 位序号。写帧总长度为 `len + 6`，最大 261 字节。接收端须能接收上述上限内的完整帧。

| `type` | 用途                    | `len` | 校验通过后的操作                           |
| ------ | ----------------------- | ----- | ------------------------------------------ |
| `0x00` | SSD1309 命令            | 1–255 | 转发 `00 + payload`                        |
| `0x40` | SSD1309 GDDRAM 数据     | 1–255 | 转发 `40 + payload`                        |
| `0x01` | 读取 SSD1309 状态寄存器 | 0     | 采样面板状态，将原始字节放入本帧的成功回执 |
| `0x7F` | 同步会话（`SYNC`）      | 0     | 序号固定为 0，按第 4 节复位协议状态        |

其他 `type` 为保留值。原生 SSD1309 接收其原有控制字节与载荷。桥接器须剥离 v3 的长度、序号和 CRC，内部查询和同步帧由桥接器处理。

## 3. 链路回执

```text
flags | last_ok_seq_L | last_ok_seq_H | value | CRC_L | CRC_H
```

| 字段             | 含义                                                                |
| ---------------- | ------------------------------------------------------------------- |
| `flags` bit 7    | `LAST_OK_VALID`。置位时，`last_ok_seq` 和 `value` 有效              |
| `flags` bit 6    | `BUSY`。置位时，接收端仍在校验、处理已接纳的帧或等待其下游 I/O 停止 |
| `flags` bits 5–0 | 最近发布的处理状态或接收事件                                        |
| `last_ok_seq`    | 最近成功的普通帧序号，低字节在前。`LAST_OK_VALID=0` 时两字节均为 0  |
| `value`          | 最近成功帧是面板状态查询时为面板状态字节，其余情况为 `0x00`         |
| `CRC_L`、`CRC_H` | 前 4 字节的 CRC-16/MODBUS                                           |

| 状态码 | 名称                 | 含义                                                                       |
| ------ | -------------------- | -------------------------------------------------------------------------- |
| `0x00` | `NEED_SYNC`          | 从机启动后等待同步                                                         |
| `0x01` | `SYNCED`             | 已建立空会话，普通帧从序号 1 开始                                          |
| `0x02` | `PENDING`            | 帧正在校验或处理                                                           |
| `0x03` | `OK`                 | 普通帧处理成功，或同一成功序号的重发已被去重                               |
| `0x04` | `CRC_ERROR`          | 完整写帧的 CRC 不匹配，已丢弃                                              |
| `0x05` | `FORMAT_ERROR`       | 长度不符、帧类型非法、类型与载荷长度不匹配，或写事务以 repeated START 中断 |
| `0x06` | `BUSY_DROP`          | 写事务开始时缓冲仍被占用，新写帧已丢弃                                     |
| `0x07` | `RX_OVERFLOW`        | 新写帧超过接收容量，或硬件接收 FIFO 溢出，已丢弃                           |
| `0x08` | `RX_TIMEOUT`         | 接收截止前未收到 STOP，半帧已丢弃                                          |
| `0x09` | `OUT_OF_SEQUENCE`    | CRC 合法的普通帧序号偏离会话顺序，需要重新同步                             |
| `0x0A` | `DOWNSTREAM_UNKNOWN` | 下游操作出错或超时，可能已经产生部分效果，需要重新同步                     |

其余状态码保留。`OK` 须携带有效的成功记录。`SYNCED` 表示空会话，成功记录须无效，主机等 `BUSY=0` 才完成同步。主机遇到未知状态码或字段组合与其含义冲突时，终止操作并报告协议错误。

回执从同一份状态快照生成，每次读取从第一个字节开始。短读、完整读取、读事务结束均不改变回执。错误事件可以更新结果码，最近成功序号与其 `value` 继续保留。损坏的写帧可能含损坏的序号，因此 `CRC_ERROR`、`FORMAT_ERROR` 等接收事件只作诊断。`last_ok_seq` 始终来自已校验并处理成功的帧。写后立即读允许暂时返回上一份合法快照，主机按第 6 节判定。

## 4. 会话、序号与去重

主机对设备地址拥有独占的协议会话。同一地址一次只允许一笔普通帧待确认，写入、读取回执和重发由同一会话串行管理。

1. 接收端启动时设置 `NEED_SYNC`，只允许合法的 `SYNC` 建立会话。主机启动或出现需恢复的错误后，先等待旧 I/O 结束，再发送 `SYNC` 并读取回执。
2. 接收端在空闲时接受合法的 `SYNC`，清除最近成功序号与样本，将期望序号设为 1，公布 `SYNCED`。`SYNC` 不调用面板操作。重复发送 `SYNC` 在尚无普通帧进入的新会话中效果相同。主机只在同步阶段重发 `SYNC`。发送调用返回后至少等待 `T_PUBLISH`，再采信 CRC 合法且两标志位均为 0 的 `SYNCED` 回执，防止将读到的旧快照当成本次同步结果。
3. 接收端校验普通帧后，若其序号等于最近成功序号，则返回已缓存的成功结果，不再访问面板。若等于期望序号，则处理一次。成功后更新最近成功序号与样本，并令期望序号按 16 位模加一（`0xFFFF → 0x0000`）。其他序号触发 `OUT_OF_SEQUENCE`。
4. 校验失败、丢弃或接收超时均不推进序号。主机重发须使用原序号和相同帧字节，只有确认成功才推进序号。
5. `NEED_SYNC`、`OUT_OF_SEQUENCE`、`DOWNSTREAM_UNKNOWN` 保持到下一次成功同步。期间普通帧一律丢弃，诊断事件可另行计数。仍有下游操作在进行时，接收端须等待其停止后才能接受 `SYNC`。

同一会话的去重记录存于接收端运行状态。任一端重启、出现持久恢复状态，或主机无法确认某帧的结果时，主机须结束原会话。建立新会话后，显示控制端重新初始化面板并按需要重推完整显示内容。SSD1309 页寻址下，GDDRAM 写入会推进列指针，直接重放结果未知的局部数据帧可能写到其他列。 [Solomon Systech SSD1309 数据手册 §10.3](https://buydisplay.com/download/ic/SSD1309.pdf#page=36)

## 5. 接收端处理规则

1. **地址匹配。** 匹配本设备的写地址后启动接收定时。若上一次处理仍占用单帧缓冲，本事务自起点进入丢弃状态。持续从 FIFO 取走字节并丢弃，直到 STOP 或中断。收到 STOP 后发布 `BUSY_DROP`，即使原缓冲在本事务中途释放也继续丢弃。禁止覆盖正在处理的帧。若处于第 4 节规定的恢复状态，则保持该状态，另记接收事件。回执状态与发送快照的存储独立于单帧缓冲。
2. **接收中。** 原始字节计数最多允许 261 字节进入缓冲。检测到帧超出容量或硬件溢出时，继续排空可读取的 FIFO 字节，等到 STOP 后报告 `RX_OVERFLOW`。如果接收截止前未见 STOP，丢弃整帧，复位解析状态并报告 `RX_TIMEOUT`，保持最近成功序号。超时后的遗留字节和迟到的 STOP 不得提交该帧。新的接收从下一次可识别的写事务边界开始。
3. **STOP 后判定。** 对正常收齐的帧，先检查实际接收长度是否等于 `len + 6`，再校验 CRC，随后检查帧类型、该类型的载荷长度限制和序号。按此顺序发布错误，校验成功才执行或转发。只有超过实际缓冲或 FIFO 溢出才判为 `RX_OVERFLOW`，`len` 与实际长度不符属于 `FORMAT_ERROR`。
4. **执行与回执。** `OK` 在命令或数据全部通过下游 I2C 转发成功后发布。面板查询在取得有效的状态字节后发布 `OK`。接收端若遇到下游错误、下游处理超时，或无法确定操作是否全部完成，须发布 `DOWNSTREAM_UNKNOWN`，保持最近成功记录并等待重新同步。模拟器在对应操作完成后发布 `OK`。
5. **短间隔读取。** 接收端在协议允许的任一独立读事务中都应能发出一份完整合法的快照。读事务期间使用固定快照，后台更新从下一次读事务起可见。硬件无法及时切换 FIFO 时，可先提供上一份完整快照，并满足第 7 节的发布时限。接收端不得依赖主机无界地容忍 clock stretching。部分从机控制器（例如 ESP32）不支持从机 clock stretching。 [Espressif I2C 从机说明](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/peripherals/i2c.html#i2c-slave-controller)

超时使协议解析器恢复到接收边界。若 SDA 或 SCL 仍被拉低，须由控制器及硬件按总线恢复规则处理。 [NXP UM10204 §3.1.16](https://www.nxp.com/docs/en/user-guide/UM10204.pdf#page=19)

## 6. 主机确认与重试

主机以一次写事务发送完整帧并产生 STOP，再读取固定 6 字节的回执。短写按传输错误处理，剩余字节不得作为另一次事务补发。回执长度、CRC 和状态码均合法时才解析状态。普通帧的确认按下表处理，当前帧在确认之前保持原序号。存在多个现象时按表从上到下匹配，总截止时间始终优先。

| 所见结果                                             | 主机行为                                                                                                         |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `NEED_SYNC`、`OUT_OF_SEQUENCE`、`DOWNSTREAM_UNKNOWN` | 终止本次操作并上报，进入会话恢复。即使回执保留了旧成功记录，也先处理会话故障                                     |
| `LAST_OK_VALID=1` 且成功序号匹配                     | 确认当前帧成功。面板查询从 `value` 取状态值。结果码可能同时记录后续接收事件                                      |
| 回执短读、CRC 错误，或 I2C 传输错误（含事务超时）    | 等待底层 I/O 结束且总线可用，先重读回执。多次读失败后，只有在满足本节重发时机与总时限时才可重发原帧              |
| `BUSY=1`                                             | 延时后继续读，直到空闲或总截止时间到达                                                                           |
| `CRC_ERROR`、`FORMAT_ERROR`、`RX_TIMEOUT`            | `T_PUBLISH` 窗口过后，若无匹配成功且操作已空闲，可重发原帧。结果码本身无法证明本帧未执行                       |
| `BUSY_DROP`、`RX_OVERFLOW`                           | 忙而丢弃时延时，等空闲后用原序号重发。主机在本地拒绝超出上限的帧。合法大小的帧若反复出现接收溢出，按链路异常上报 |
| 其他合法状态且成功序号未匹配                         | 延时后继续读。若到结果时限仍无可采信的结果，可用原序号、原字节重发                                               |
| 总截止时间到达                                       | 停止启动新的读写，向上层报告确认失败。未获得可信结果时标为「结果未知」，结束当前会话                             |

确认失败的写事务仍可能已被接收端处理。主机以最近一次写调用返回为起点计算发布和结果等待窗口。若尚未确认成功且能读取到合法的 `BUSY=1`，应继续读到空闲或总截止时间到达。若一直读不到合法回执，只能在一个结果时限过去且总线可用后重发同一普通帧，依赖接收端的同序号去重。当前发送端要求最近一次读事务已返回至少一个字节，才开始重发。禁止在同一个阻塞 I/O 尚未结束时并发发起新事务。Linux `I2C_TIMEOUT` 作用于适配器，应用层总截止时间负责禁止开始后续重试，正在等待的单次 I/O 由内核驱动处理。 [Linux i2c-dev 实现](https://github.com/torvalds/linux/blob/master/drivers/i2c/i2c-dev.c)

## 7. 时限与联调基线

下表列出协议时限和当前发送端使用的参数。接收端应满足协议时限，并在目标硬件上验证最坏延迟。

| 参数                     | 数值   | 起算点和用途                                                                        |
| ------------------------ | ------ | ----------------------------------------------------------------------------------- |
| 接收截止 `T_RX`          | 50 ms  | 从从机匹配写地址到 STOP，限制半帧占用                                               |
| 回执发布 `T_PUBLISH`     | 5 ms   | 从 STOP 到对应的新状态可读，允许先发布 `PENDING`                                    |
| 结果时限 `T_RESULT`      | 100 ms | 从 STOP 到终态可读，包含下游操作。到期后下游还未明确完成时发布 `DOWNSTREAM_UNKNOWN` |
| 轮询/忙退避间隔 `T_POLL` | 2 ms   | 同一帧两次状态读取之间，以及忙状态后的最短等待                                      |
| 主机单事务超时 `T_IO`    | 100 ms | Linux 发送端在打开设备时设置适配器级超时；该设置关闭连接后不会恢复，部署时核对适配器和共享总线设备的要求 |
| 主机单帧总时限 `T_FRAME` | 500 ms | 从首次发送计时，涵盖重复读、退避与重发。同步阶段使用同样的总时限                    |

100 kHz 下最大 261 字节写帧加地址约需 23.6 ms 纯线上时间，`T_RX` 还须覆盖合法的时序余量。按当前每屏 24 笔写事务、每笔一次 6 字节回执计算，新版上游纯线上约 125 ms/屏。如果每笔确认前还须等待另一个 100 kHz 总线上的完整转发，两段串行约 223 ms/屏。实际耗时还包括轮询、调度和重试。 [当前逐页推帧实现](../i2c_display_driver/src/display/ssd1309.rs#L77-L86)

## 8. 一致性向量与联调

以下均为十六进制线上字节，不含 I2C 地址。按顺序验证同步、命令、数据和面板查询。故障向量除另行注明外，以最近成功帧为序号 1 的命令为前置状态。

| 输入或情形                                                         | 预期                                                                       |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 从机启动后直接读                                                   | `00 00 00 00 00 24`（`NEED_SYNC`）                                         |
| 写 `7F 00 00 00 19 F0`                                             | `01 00 00 00 01 D8`（`SYNCED`）                                            |
| 写 `00 01 01 00 AE F5 80`                                          | 成功转发 `00 AE`，回执 `83 01 00 00 78 60`                                 |
| 再写 `00 01 01 00 AE F5 80`                                        | 同一成功回执，面板转发共一次                                               |
| 写 `40 02 02 00 01 02 F6 F2`                                       | 成功转发 `40 01 02`，回执 `83 02 00 00 88 60`                              |
| 写 `01 00 03 00 01 28`，面板返回 `81`                              | `83 03 00 81 19 C0`，重读/重发继续返回同一状态样本                         |
| 写 `40 02 02 00 01 02 F6 F3`                                       | 正常 I2C 接收，STOP 后发布 `84 01 00 00 79 14`（`CRC_ERROR`），不转发      |
| 写 `40 03 02 00 01 02 F6 F2` 并提前发出 STOP                       | `85 01 00 00 78 E8`（`FORMAT_ERROR`），不转发                              |
| 写 `40 02 02` 后未在时限内发 STOP                                  | 总线重新可读后返回 `88 01 00 00 7A 44`（`RX_TIMEOUT`），迟到的 STOP 不提交 |
| 序号 2 仍在处理，另一写事务因占用缓冲被丢弃，读取时序号 2 仍在处理 | `C6 01 00 00 6D 6C`（`BUSY_DROP`，`BUSY=1`），最近成功序号仍为 1           |
| 序号 3 的面板状态查询成功返回 `81` 后，序号 4 下游写失败且已停止   | `8A 03 00 81 1A 5C`（`DOWNSTREAM_UNKNOWN`），同步前禁止继续转发普通帧      |
| 成功序号 `0xFFFF` 后，下一笔命令以序号 `0x0000` 成功               | `83 00 00 00 29 A0`，有效位仍为 1                                          |

上表 `40 03 02 00 01 02 F6 F2` 同时含长度不符与 CRC 错误（帧体实际 CRC 为 0x32CB，线上 `CB 32`；尾部 `F6 F2` 是上一行数据帧的 CRC）；期望 `FORMAT_ERROR` 用于验证“先长度后 CRC”的判定顺序。只验证长度失配时可用 `40 03 02 00 01 02 CB 32`。

联调至少覆盖以下情况：

- 故意破坏读回的 CRC，再读能取得原成功回执。若改为重发同序号，面板仍只接收一次。
- 写事务返回超时但面板已接收。主机恢复后先读回执，核对序号并避免重复写入。
- 忙时送入第二帧，验证 FIFO 仍被排空、第二帧未覆盖第一帧且成功记录可重复读。另用超长帧验证 `RX_OVERFLOW`。
- 发送短帧、超长帧、提前 STOP、丢失 STOP 和 repeated START。用逻辑分析仪确认 CRC 错误以 STOP 后回执报告，CRC_H 仍按常规接收。
- 一端重启或下游可能部分执行时，主机结束原会话，完成同步后重新建立面板状态。
